## Keyboard regression found during this audit — FIXED

### Root cause

Localization builders used broad plain-string replacement on complete HTML files. This allowed visible UI translation tokens such as `Keyboard`, `Left`, and `Right` to mutate program structure inside the inline keyboard script and DOM IDs.

Examples observed in generated locale output included:
- `fitKeyboard` → translated function identifier
- `startKeyboard / exitKeyboard / resetKeyboard` → translated DOM IDs
- browser-standard key-code strings containing `Left / Right` could be translated

Vietnamese exposed the defect immediately because `fitKeyboard` became an invalid JavaScript identifier containing a space. Other languages could remain syntactically valid while silently changing browser key-code comparison behavior.

This explains why a global build could succeed while locale keyboard behavior regressed.

### Fix

- Added `tools/normalize_generated_keyboard.py`.
- After all locale builders finish, generated English keyboard behavior JS is treated as the structural source of truth and restored into every localized keyboard page.
- Visible surrounding UI remains localized while browser key codes, function names, DOM references, modifier rules, Fn state, and fullscreen logic remain canonical.
- Added `tools/validate_dist.py` as a mandatory pre-deploy gate.
- Workflow now blocks deployment unless the full artifact passes structure, references, SEO, JS syntax, keyboard invariants, ad-slot placement, and localization checks.
